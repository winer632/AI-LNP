4. GO-005 与 GO-006 的机制差异

为什么同一张补充材料里，相邻两表一个能恢复一个不能？因为 GO-005 的值在正文里被引用了：

block_type = paragraph   source_kind = pmc_xml

  "…whereas LSECs showed gene editing rates of approximately
   16.50% ± 2.96% (Figure 6A; Table S1)."

而正文从头到尾没有引用过插入频率的数值。1.01 只存在于 Table S2 的单元格里。 于是规律非常清楚：

  • 被正文引用的数值 → 现有链路可恢复
  • 只存在于补充材料表格的数值 → 现有链路不可见，必然丢失

uniparse 恢复的正是后一类。

八、P3｜候选必答前移

防止新的静默遗漏。

P3

把 repair 阶段的约束前移到第一次调用

目标：结构性防漏 ｜ 成本：改 prompt 与 contract

docs/extraction/corrected_compact_workflow.md 已经写明这条原则：

A task response must account for every candidate ID;
silence is not a valid disposition.

但它只在 repair 阶段执行，第一次调用没有执行。 结果是 GP-001 / GP-003 / GP-009 第一次调用返回 0 条 outcome， 而没有人知道这是「论文里真没有」还是「模型漏了」。

  1. 抽取前，从完整证据视图确定性枚举出 (实验 × 终点) 网格
  2. 每个格子是一个必须回答的槽位，随 packet 一并下发
  3. 模型对每个槽位必须给出「值」或「显式 unresolved + 理由」
  4. validation 校验槽位覆盖完整性，缺失即判定 invalid
思路来源 cuhk_law 项目的核心可迁移经验：用确定性枚举取代相似度选择。 它按 chapter 把该章全部法条无差别拉出（无 top-k、无预算裁剪）， 召回由架构保证而非由打分器决定。可迁移的是这个原则， 不是知识图谱本身 —— 引入 Neo4j 对提高单篇 recall 帮助有限。

十、风险与边界

uniparse 是 VLM 驱动的解析器，不是确定性解析器 它跑在 vLLM 上（/app/models/uniparse，max ctx 16384）。 那份漂亮的表格 HTML 是模型输出，不是版面真值。 前置验证证明它在 GP-006 上是对的，但这不等于它在所有论文上都对。 必须对 uniparse 的表格与图注结果额外加一层校验（建议：与表格裁剪 PNG 交叉核对， 或对关键数值要求人工确认），否则只是把幻觉从抽取阶段挪到解析阶段 —— 而且更隐蔽，因为它长得像结构化数据。
不要因为召回上升就宣布成功 在 P0-b 完成前，任何召回提升都无法与「抽得更激进带来的噪音」区分开。
GO-017 的性质 Day7 v4.1 与 Day8 两次独立裁定均判定可得文本属推断而非实测（D8M-0108）。 这是科学裁定标准问题，不是工程问题。 强行做到 15/15 大概率意味着放松了裁定标准 —— 那不是提升，是拆门槛。 现实终点是 13–14/15。
7022 服务端不做改动（已确认） 该容器的 heading_level_llm 配置缺陷已定位，但不重启、不改配置： GPU4 由 7 个容器共享（uniparse 45.7 GB / 其余 26.0 GB / 共 71.7 of 81.9 GB）， 而 vLLM 以 --gpu-memory-utilization 0.8（65.5 GB）启动， 停机后可用仅约 55.9 GB，重启大概率因显存不足失败， 且 RestartPolicy = no 无自动恢复。此外 config.yaml 在镜像层内、 无挂载，改动不持久。 AI-LNP 侧「不传 heading_level_enabled」即可完全规避，零风险。 治本的代码补丁已另行提交至本地分支 fix/heading-level-llm-base-url-validation （上游仓库为 gitlab.sh.sensetime.com/llm-data/uniparse-pdf，未推送）。
